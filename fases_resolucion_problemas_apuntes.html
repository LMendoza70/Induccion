Apuntes de clase — Análisis del problema + 3 ejemplos

La ingeniería de software propone una serie de fases que hay que seguir para desarrollar un programa informático. Es como una receta de cocina: si te saltas un paso, el platillo (el programa) sale mal. Aquí va el mapa completo:

1. Ingeniería de sistemas
→
2. Análisis de requisitos
→
3. Diseño
→
4. Codificación
→
5. Pruebas
→
6. Mantenimiento

(las flechas dobles del diagrama original indican que se puede regresar a una fase anterior si algo no cuadra — nada es 100% lineal)

① Ingeniería y análisis del sistema

  • El software nunca vive solo — siempre es parte de un sistema más grande.
  • Se estudia el sistema completo: requisitos de TODOS sus elementos (sean o no informáticos).
  • De ahí se separa el subconjunto que le corresponde al software.

② Análisis de requisitos del software

  • Se estudia qué necesita cumplir el programa para funcionar bien.
  • Se hace junto con el cliente — él es quien manda sobre qué necesita.
  • Aquí se fijan las características básicas del sistema.
Esta fase es la más importante de descuidar: si el análisis está mal, todo lo que sigue hereda el error (diseño, código, pruebas...).

③ Diseño

Ya con los requisitos claros, se estudian las partes que va a tener el programa:

  • Estructuras de datos — cómo se va a guardar/organizar la información.
  • Arquitectura del software — qué módulos hay y cómo se relacionan entre ellos.
  • Detalle procedimental — el algoritmo específico de cada módulo.

④ Codificación

Es traducir el diseño a un lenguaje de programación real (Java, C#, Python...). Ojo: codificar es la parte más "mecánica" — si el diseño ya está bien hecho, esta fase debería ser casi automática.

⑤ Pruebas

Se diseñan datos y tareas para poner a prueba la aplicación antes de que llegue a producción. Aquí se detectan errores que se nos pasaron en las fases anteriores.

⑥ Mantenimiento

El programa sigue cambiando después de entregado, por dos motivos:

  • Errores detectados ya en producción (bugs).
  • Nuevas necesidades del cliente o cambios en sus procesos.
• • •

Análisis del problema

Antes de programar cualquier cosa, hay que entender el problema. Un análisis simplificado responde tres preguntas clave:

1) ¿Qué queremos obtener? → Datos de salida

Hay que especificar exactamente qué produce el programa y en qué formato/tipo (¿un número? ¿una fecha? ¿texto?).

2) ¿De qué datos disponemos? → Datos de entrada

Qué información nos dan para trabajar, y también su formato.

3) ¿Cómo convertimos entrada en salida? → Proceso

Una idea general de los pasos a seguir. Esto ya empieza a perfilar el futuro algoritmo, y ayuda a detectar si nos falta información desde el inicio.

Truco para no perderte: siempre llena mentalmente esta tabla antes de programar — Salida / Entrada / Proceso. Si no puedes llenar las tres columnas, todavía no entiendes bien el problema.
✎ EJEMPLOS ✎

Ejemplo 1.1 — Multiplicar sin usar la multiplicación explicado en clase

Enunciado: Se desea realizar un programa que permita multiplicar dos números enteros positivos sin utilizar el operador de multiplicación.

Datos de salidaEl producto de los dos números — será también un entero positivo.
Datos de entradaDos números. Se supone que son enteros positivos, aunque no se va a comprobar (si no lo son, el programa no funcionaría bien).
ProcesoAcumular el primero de los números tantas veces como indique el segundo. Es decir: si tenemos a y b, vamos sumando a a un acumulador, repitiendo esa suma b veces.

Ejemplo concreto: 4 × 3 → acumulador = 0 → 0+4=4 → 4+4=8 → 8+4=12. Sumamos 4, tres veces (porque b=3), y llegamos a 12. Esa idea de "sumar repetidamente" ya es casi el algoritmo — solo falta traducirlo a pseudocódigo o código.

Ejemplo 1.2 — División por restas sucesivas para resolver tú

Enunciado: Se desea un programa que calcule cuántas veces cabe un número entero positivo b dentro de otro número entero positivo a (es decir, el cociente de a ÷ b), sin usar el operador de división, solamente restando.

Resuélvelo respondiendo tú mismo estas preguntas antes de programar:

  • ¿Cuáles son los datos de salida y qué formato tienen?
  • ¿Cuáles son los datos de entrada?
  • ¿Cómo se procesan los datos de entrada para llegar a la salida? (pista: piensa en restar b a a repetidamente y contar cuántas restas alcanzas a hacer antes de que el resultado sea menor que b).

Ejemplo 1.3 — Suma de los dígitos de un número para resolver tú

Enunciado: Se desea un programa que, dado un número entero positivo, calcule la suma de todos sus dígitos (por ejemplo, para 4527 el resultado sería 4+5+2+7 = 18).

Haz tu propio análisis del problema:

  • ¿Qué se quiere obtener (salida) y de qué tipo es ese dato?
  • ¿Qué dato(s) se reciben como entrada?
  • Describe en pocas palabras el proceso: ¿cómo se puede ir "separando" un dígito a la vez de un número? (pista: piensa en el residuo de dividir entre 10, y luego en dividir el número entre 10 para "quitar" ese dígito).
• • •

Recuerda: el Análisis del problema (salida / entrada / proceso) es el paso previo obligatorio a Diseño. No te avientes directo a codificar — ahí es donde más tiempo se pierde arreglando errores que se pudieron evitar pensando un poco más antes.
